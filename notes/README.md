### アプリ（Go）の主な変更

- **通知を SSE にした**: アプリ内の hub で、状態が変わったときにユーザーと椅子へ push する。再接続したときは最新の状態から送り、古い状態は送らない
- **メモリに持つようにしたもの**
  - 椅子: 位置・総走行距離・現在のライド・active
  - ライド: 行・料金・最新の status・椅子ごとの評価の集計・売上の記録
  - 待ちライドの一覧
  - access_token と ID から引くユーザー・椅子・オーナー
  - 決済トークン・決済 URL
- **DB への書き込み**
  - `chair_totals`（総距離と最新位置）は 1 秒ごとにまとめて upsert する
  - `ride_statuses` は 50ms ごとにまとめて INSERT する
  - `chair_locations` には書かない（どこからも読まなくなったため）
  - SIGTERM を受けたら残りを書き出してから終了する
  - 起動時と initialize のときに DB からメモリへ読み込み直す
- **マッチング**: アプリ内の goroutine で 50ms ごとに回す（isuride-matcher は使わない）
  - 3 秒以上待っているライドは、古い順に空き椅子の台数ぶんを選び、その中で到着時間（距離÷速度）が短い組から割り当てる
  - 残りの空き椅子は、全ペアを到着時間でソートして貪欲に割り当てる
  - 計算はロックの外でする
- **評価 API**
  - トランザクションを使わず、キャッシュで状態を確かめる → 決済 → `UPDATE rides` を 1 本
  - 決済は `Idempotency-Key=ride_id` を付けて、すぐにリトライする。keepalive を効かせた専用の http.Client を使う
  - 決済は評価を確定する前に済ませる（非同期にすると CODE=34 で fail した）
- **nearby-chairs**
  - MATCHING の通知を椅子へ送る前の椅子は「空き」として含める
  - 解放してから 1 秒以内の椅子は除外する
  - retrieved_at は、椅子の一覧を取り出したあとの時刻にする
- **その他**
  - インデックスを追加した
  - `users.username` の UNIQUE を外した。ベンチが同じ名前で登録し、201 を期待するため
  - 招待登録は、`FOR UPDATE` をやめて招待コードごとの mutex にした。グローバル mutex だと 10 秒のタイムアウトが出た
  - 大きい JSON はアプリで gzip して返す

### 分かったこと

- 途中から、空き椅子の数がスコアを律速していた。数百件のライドが待っている一方で、空き椅子は数台しかなかった
- 椅子 1 回のサイクルは次の合計（各フェーズの平均。最後の計測時点）
  - 迎車: 約 0.6〜0.8 秒
  - 乗車: 約 0.06 秒
  - 移動: 約 0.6 秒
  - 評価: 約 0.8 秒
- 「ARRIVED を push してから評価リクエストが届くまで」は平均 548ms だった。これはベンチ側の挙動だと判断した
- 椅子は座標を送るリクエストが返ってくるまで移動しない。そのため nginx の応答遅延（CPU が張り付いて約 10ms）がそのまま移動時間に効く。HTTP/2 と nginx の調整が効いたのはこのためだと考えている
- 決済のモックは、どのリクエストにも約 53ms かかり、約 69% が 500/502/504 を返す。同時実行数を絞っても失敗率は変わらなかった。リトライの sleep をなくすのが最善だった

### 効かなかったもの・失敗したもの

- 純粋に貪欲なマッチング: 古いライドが割り当てられずに残り、CODE=32 で fail した。urgentWait を 15 秒にすると、不満は減ったがスコアは下がった。2〜5 秒の範囲ではスコアの差が誤差に埋もれた
- 決済の非同期化: 評価が終わったのに支払われていないライドがあると判定され、CODE=34 で fail した
- 決済の同時実行数を 10 に制限: 失敗率は変わらず、遅延だけ増えた
- TLS 終端の分散（isu1 は stream で L4 振り分けだけ、終端は isu2/isu3）: isu1 のローカルの TLS バックエンドへ回すと RST が多発した。isu2/isu3 へ回すと pass はしたが改善しなかった。isu2 は MySQL と nginx を同居させたので飽和した
- KTLS、`proxy_buffering off`、keepalive の延長: 効果なし、または悪化
- `GET /api/app/rides` のメモリ化（23:22）は 681k / 780k で差が出なかったので戻した
- 1 回のベンチのぶれが ±5〜10% あり、小さな改善は判定できなかった。複数回回して平均を取るべきだった
